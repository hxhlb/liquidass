Dynamic Island black/white text — banana42 test plan

Current implementation and measured proof: DYNAMIC_ISLAND_TEXT_RESEARCH.txt.
Scope: Light black text, Dark white text. No extra setting or gradients.
The failed banana39–41 content-specific trait/palette/scene adapters were removed.
Previous experiments remain in Git history; their host checks were not phone proof.

Manual device acceptance (agent must not install or restart):
1. Install the matching package yourself and reload the relevant UI processes
   when ready. The package postinst performs no automatic reload.
2. Enable the existing Dynamic Island glass switch. With a Light system theme,
   check music title/artist/time and screen-recording text, collapsed and expanded.
3. Check long scrolling titles, attributed strings and changing timer values.
   Layout, font, clipping and opacity should remain native; artwork is unaffected.
4. Switch Dark -> Light while content remains active. Text should be white in
   Dark and black in Light, with secondary opacity retained.
5. Disable island glass, then inspect ordinary App pages, Lock Screen and Control
   Center text. Their original drawing and colors should remain unchanged.
6. Report the actual visible result, including the content/activity and state.
   Do not infer failure merely from UILabel.textColor remaining white: this
   implementation changes the final glyph raster, not the stored text attributes.

Known earlier device observations:
- banana40 was installed on iPhone 13 Pro Max / iOS 17.3.1 RootHide. Both music
  and recording services mapped liquidass.dylib; injection was not absent.
- SpringBoard was Light while the music Activity scene was forced Dark.
- banana41's scene hook was loaded and changed that scene to Light, but the user
  still saw white text. Scene appearance alone therefore did not solve the issue.
- Attaching Frida 16.1.4 to MediaRemoteUI triggered EXC_GUARD at
  task_swap_exception_ports. No further content-process attach was attempted.
  SpringBoard-only snapshots were read successfully. Do not silently retry the
  known failing attach path or alter device security/tooling.

iOS 16 startup remains a separate issue:
- The initial supplied report matched banana33's old keyboard callback.
- Later reports confirm a recurring GainMap encoder crash in backboardd on
  iOS 16.3 / iPhone14Pro. See DYNAMIC_ISLAND_STARTUP_INVESTIGATION.txt.
- This text package is not a verified fix for that startup failure. Do not ask
  the affected iOS 16 tester to repeat userspace restart as text acceptance.
